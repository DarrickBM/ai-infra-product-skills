# 私有化部署选型与测算

## Overview

把「一批卡 + 一组场景」变成一份选型与部署建议：**筛候选 → 筛可行 → 定编队形态
与配比 → 配第三方佐证**。

前三步都要走，跳过任何一步都会得到装不下、并发算错、或结构不合理的结论。第四步在联网
工具可用时做——跳过它方案只剩供应商自述，客户没有理由信选型。

## 这个 skill 的边界（先读这一段）

**零外部凭据。** 只用 `data/` 下打包的三样东西：公开版方法论、模型目录快照、公开硬件
规格。**不要试图连任何在线数据源、内部系统或文档服务**——没有配，也不该配。
目录外的模型不在候选池里。

**输出的所有并发数字都是 roofline 物理包络，不是可承诺并发。** roofline 不建模预填充
与解码互相挤占、请求排队、P95 尾延迟，真实工程可承载约低一个数量级。每份输出都必须
写明这一点，并注明「合同并发与 SLA 数字需由供应商按实测工程数据出具，或做 PoC 实测」。
这条不能省——省了就是给出一个高约十倍的承诺。

**目录只含开放权重且可自建的模型。** 这个 skill 做的是私有化部署——闭源 / API-only 的
模型放不到客户的卡上，给出来就是无法交付的选项。客户问到某个闭源模型，答「本方案只覆盖
可私有化部署的模型，托管调用需 供应商另行对接」，**不要凭记忆给它的参数或部署方式**。

**目录是快照，且语言类只留窗口内发布的型号**（`catalog.py` 会打印快照日期与截止日）。
语言模型迭代太快，固化全量历史库只会让方案引用两年前的型号。代价是新模型不在目录里
——**联网可用时按 `references/catalog-refresh.md` 分模态现搜补上**，补进来的一律标注
「目录外候选，需供应商确认可供」，且同样只收开放权重且可自建的。方案里写明快照日期。

**方法论只有公开版**（`data/methodology-public.md`：三维定位、合规筛查项、失效类型
分层、RAG 检索侧判据，都带公开出处）。**没有的是**：按组合给的首选/备选模型清单、
阻断清单、微调数据量与预算、报价与商务、可承诺的 SLA 数字。这几项方案里一律写
「需供应商出具」，**不要凭记忆补**。

## 第一步：定位与筛候选

**先读 `data/methodology-public.md`**，按它的三维定位（D1 行业 / D2 业务应用 /
D3 主场景语言）给客户定位。

**另外问一句「不出域到什么程度」**——业务数据 / 全部数据 / 完全离线（PHI、主权数据）。
这个不影响选型（候选本来就全是可自建的），但第三档要按离线运维设计：权重离线导入、
无外呼、审计留痕，**改的是交付计划不是配置**。方法论第二节有分档表。

硬件侧另外问清两件事，缺了没法测算：

1. **卡是什么** — 型号、几台、每卡实测显存（`nvidia-smi`）、有没有 RDMA
2. **上下文档位** — 各场景典型输入长度，这直接决定 KV 池

再按场景收敛：

| 场景 | 收敛方向 |
|---|---|
| 通用办公问答 | 吞吐优先 → 小激活参数 MoE，档位 8K 为主 |
| 知识库 / RAG | 上下文优先 + 检索侧模型（Embedding + Reranker），档位 32K 起。**先按方法论第三节诊断失效类型**——不是所有知识问题都该上 RAG，更不该上来就说微调 |
| 客服 | 吞吐 + 低延迟，模型不必大 |
| 代码 | 质量优先，看编码类基准；上下文往往要 128K+ |
| 图文混合 | **先查 `input_modalities`**，别默认要旁挂 VLM（见坑二） |

**首选与备选不要同厂**（看 `developer`）——一家的许可或供货出问题时要有退路。

**候选不够就现搜。** 快照超 30 天、主场景是语言类、客户点名了目录外的模型、或筛完凑不出
三档编队——任一条成立，按 `references/catalog-refresh.md` 分模态搜最新模型补进候选池。
补进来的**同样只收开放权重且可自建的**，且必须先从 HF 取到权重体积、config、LICENSE 正文
才能进编队测算；取不到就只列「值得关注，待评估」，不进测算数字。**不写回目录文件**，
只在本次会话里生效。

合规筛查按方法论第二节的四个检查项走（Model Card / 许可×司法辖区 / AI Verify 预检 /
风险分档）。**具体的阻断清单需供应商出具**，本版只有检查项。

## 第二步：筛可行

从目录拿到候选后，逐个过三道闸：

1. **装得下吗** — 权重 + KV 池落在「总显存 × 92%」内（8% 给激活/碎片/CUDA Graph）
2. **这张卡跑得了它的权重精度吗** — 见坑一
3. **许可能不能商用** — 见许可闸门

## 第三步：定编队形态与配比

**先定形态，再算配比。** 形态由「算力预算 ÷ 场景需求」决定，不是固定的。

先算一个比值：**候选主力模型的权重 ÷ 可用显存**。

| 权重占比 | 形态 | 说明 |
|---|---|---|
| **> 50%**（单机塞大模型） | **1 个大模型 + N 个小模型** | 大模型吃显存、接最难的少数请求；小模型吃流量、接绝大多数。此时大模型位**独占**——任意两个大模型相加都超容量，只能三选一 |
| **15–50%** | **按场景配专用模型，各 1–2 副本** | 显存够放几个中等模型，不必分大小。每个场景配最合适的那个，剩余显存转成 KV 池 |
| **< 15%**（多机 / 大显存） | **每场景专用模型 + 多副本冗余** | 瓶颈从显存转到算力与可用性。同一模型开多副本做负载均衡与实例级冗余，甚至同场景放两个不同模型做 A/B |

**多台机器**：默认**每台独立编队、不跨节点 TP**（除非确认有 RDMA 且单模型确实装不下
单机）。两种排法：

- **对称**（每台一样）→ 拿节点级冗余，掉一台服务不断
- **非对称**（一台专跑大模型，其余跑前线）→ 拿能力上限，但大模型没有节点级冗余

这个取舍要写明，别只给一种。

**10 台以上**：形态问题变成容量规划问题——先按场景算总并发需求，再反推每类模型要几个
副本、占几台机，剩余机位留给扩容与灰度。这种规模下「1 大 + N 小」通常不成立。

## 第四步：配第三方佐证

联网工具可用时，给每个**入选模型**（含备选编队里的）配两类佐证：**权威榜单名次**
（开源榜 + 总榜两个数）和**社区口碑**（X 中英 + Reddit，自模型发布日起至今）。淘汰的
模型不做佐证，只留淘汰依据。

取数方法、踩坑、负面口碑的闸门判据、佐证表形态，全部见 `references/model-evidence.md`。

工具不可用就跳过，并在方案里写明「第三方佐证需供应商补充」。**绝不凭记忆编名次或
推文链接**——榜单是滚动的，编出来的链接是假的。

## 三个每次都要踩的坑

### 坑一：落盘体积 ≠ 显存占用

低比特混合精度发布越来越多，标称体积按发布精度算，换张卡就不成立。

- MoE 专家 FP4 的（如 DeepSeek V4-Flash：284B 落盘仅 167 GB）——**Hopper（H20/H800/H100）
  无原生 FP4**，要么靠引擎反量化 kernel，要么上转 FP8（约 294 GB）。**Blackwell
  （B200/B300）有原生 NVFP4，不受此限**。
- INT4 weight-only 打包的（如 Kimi K2.7-Code：1T 参数 595 GB）——Hopper 有成熟 kernel，可用。
- MXFP8 的（如 MiniMax M3：443.7 GB）——MX 是 OCP 微缩放格式，分块 scale 的 kernel 支持要实测。

**动作**：装载按**目标卡能原生跑的精度**算，低比特路径列为 PoC 实测项。**低比特也要
体现在解码吞吐里**——INT4 每参数 0.5 byte，带宽受限吞吐是 FP8 的 2 倍。

**从落盘体积到「这张卡上的体积」，三步走**：

1. **主仓的体积是发布精度的体积，不是你要的那个数。** `zai-org/GLM-5.2` 主仓
   1506.7 GB 是 BF16；单台 H20 可用才 1038 GB，照主仓的数算会直接判「装不下」，
   但它其实装得下。
2. **先找目标精度的官方权重仓。** 命名基本是 `<主仓>-FP8` / `-NVFP4`：
   `zai-org/GLM-5.2-FP8` = 755.6 GB，`Qwen/Qwen3.8-Flash-Next-FP8` = 185.5 GB。
   用 `curl -s "https://huggingface.co/api/models?search=<模型名>&limit=20"` 列一遍
   同名仓，**按 HF 官方 org 判断哪个是官方的**。
3. **官方没有目标精度的仓时，第三方量化要单独决策，不能默默采用。**
   例：`sgl-project/DeepSeek-V4-Flash-FP8`（294.0 GB）与
   `sgl-project/DeepSeek-V4-Pro-FP8`（1606.5 GB）是 SGLang 团队发的，**不是
   DeepSeek 官方 org**。用第三方量化权重要在方案里单列一条，写明：谁发的、
   许可是否继承主仓、有没有官方替代、掉点数据有没有、谁负责后续跟版。
   **拿不准就按「官方 BF16 + 引擎在线量化」算，并列为 PoC 实测项**——在线量化
   显存占用与掉点都要实测，不能拿第三方仓的数字替代。

没有目标精度的权重、也不接受在线量化时，这个模型在这张卡上就是**装不下**，按淘汰
依据写进方案，别用主仓体积硬凑一个能装下的假象。


### 坑二：多模态可能已经在小模型里

不要默认「大模型只有文本 → 旁挂一个 VLM」。**先查目录的 `input_modalities`**。

实例：Qwen3.6-27B / 35B-A3B 都是 `文本+图像+视频`，OCRBench 89.4/90.0 **高于**
Gemma 4 31B 的 86.1。再挂独立 VLM 是重复投入。语音走专用 ASR 比让 VLM 兼职更准更省。

### 坑三：知识库的算力全在重排

embedding 每块编码一次可缓存，成本可忽略。**reranker 是 cross-encoder，每个
（查询,候选）对一次完整前向，换个查询全部重算**，代价 = Top-K × 每对前向，**随参数量
线性变化**。

- 8B reranker 跑 Top-50 = 7.43 卡·秒/查询 → 知识库 1 QPS 吃掉 8 卡整机 93%，必须走
  两级（小模型粗排 → 8B 精排 Top-8，≈1.75 卡·秒）
- 0.568B reranker 同样 Top-50 只要 0.53 卡·秒（6.6%）→ **单级 Top-20 即可，两级纯属多余**

**先查候选 reranker 的实际参数量再决定单级还是两级。Top-K 上限一律不超过 20，这块必须
从算力封顶里单独扣**，不能并进 LLM 吞吐。

## 客户点名了某个模型

销售场景里客户经常直接点名（「GLM-5.2 是肯定要的」）。点名的模型**照样走硬闸门**，
但**结论不是「出局」就完事**——要给出「能上，代价是什么」，让客户自己权衡。

按闸门结果分四种，每种的说法不一样：

| 情况 | 怎么写 |
|---|---|
| **装得下，代价小** | 正常进编队，不必特别说明 |
| **装得下，但吃掉大半显存** | 照上，但必须写明连带代价：能开的副本数、有没有实例级冗余、**它排除了哪些别的模型**。例：GLM-5.2 FP8 755.6 GB 占单台 H20 可用显存 73% → 只能 TP8 单实例、无实例级冗余，且与 DeepSeek V4-Flash（294 GB）相加 1049.6 GB 超容量，两者只能二选一 |
| **主仓精度装不下，目标精度装得下** | 写明要用哪个权重仓、精度是什么、体积差多少。第三方量化仓按坑一的规矩单列一条 |
| **任何精度都装不下** | 这时才是出局。**给数字，不给结论**——「V4-Pro FP8 落盘 1606.5 GB，单台 H20 可用 1038 GB，差 568 GB」，然后给两条出路：换模型，或加机器（说明要几台） |

三条硬规矩：

- **不要为了满足点名而调宽测算**。装不下就是装不下，把 92% 的显存留量调到 98%、
  或者拿主仓 BF16 之外一个来路不明的量化仓凑数，都是在给客户一个会在 PoC 现场塌掉的方案。
- **点名模型独占大模型位时，另外两个 option 就不是「可选项」而是「替代方案」**。
  说清楚它们互斥，别让客户以为三个能同时上。
- **点名模型进了保底档要格外小心**。保底档的价值是没有未知数；一个吃掉 73% 显存、
  无实例级冗余的模型不适合做保底，即便客户点了名。

## 许可闸门

| 类型 | 处理 |
|---|---|
| MIT / Apache-2.0 | 无附加条件，最干净 |
| 署名类（如 Kimi Modified MIT） | 界面标注即可，不是禁止 |
| **书面授权类**（如 MiniMax Community：年收入 >$20M 商用须事先书面授权） | **有前置周期，签约前必须走完**；拿不到就要有不含它的备选编队 |
| 无开放权重（API-only） | 私有化部署直接出局。目录里本来就没有这类，现搜时要用 HF API 验真剔掉 |

**必须读 LICENSE 正文**，不要凭许可名下结论——"Community License" 底下的条款差别很大。
仓库里没有 LICENSE 文件、只有 model card 的 `license` 字段时，标注为「未读到正文，需
法务确认」。

## 并发口径

`scripts/fleet_sizing.py` 算的是 **roofline 物理包络**：显存带宽与算力的上限。

它回答：上下文档位开不开得了、显存够不够、编队结构合不合理。

它**不**回答：能承诺多少并发。真实工程可承载约低一个数量级（预填充与解码互相挤占、
排队、P95 尾延迟，roofline 都不建模）。

**每份输出的并发段都必须带这句**：

> 以上为 roofline 物理包络，用于验证容量与结构可行性，**不可作为对外并发承诺**。
> 合同并发与 SLA 数字需由供应商按实测工程数据出具，或以 PoC 实测为准。

## 输出

### 内容契约

```
一、场景切分          — 各场景的上下文档位与核心要求，标出主场景
二、选模型            — 三维定位 / 候选 / 硬裁剪（含淘汰依据）
                      编队形态 / 各位置的选型 / 许可筛查
                      佐证表（榜单名次 + 社区口碑 + 部署注意）
三、整机配置          — 硬件表 + 来源
四、并发与上下文包络    — 包络 / 折算到人 / 编队配比 / 口径声明 / 部署形态
五、知识库（若有）     — 失效类型诊断 / 容量 / 链路 / 检索侧模型 / 与硬件适配
六、交付形态与运行时    — 产品形态 / 不出域档位 / 运行时安全
七、后续              — 待供应商确认项、PoC 实测项
```

五项必填，任何载体下都要有：

1. **2–3 个编队方案**（主推 + 保底 + 能力上限档），保底那个许可最干净
2. **并发口径声明**——上面那段原话，不可省略、不可弱化
3. **淘汰依据**——谁被筛掉，因为装不下 / 精度跑不了 / 许可
4. **目录快照日期**（+ 语言类截止日）；若做了现搜补充，写明检索日期与哪些是目录外候选
5. **需供应商确认的事项**——首选/备选清单、阻断清单、可承诺并发、供货与商务

**硬件结论别写死在某个模型上**——"必须买大显存版因为 X 装不下"这种论据，换个主推模型
就塌。改用「装完权重剩多少 KV、并发差多少倍」这种对所有候选都成立的说法。

### 载体

默认在对话里直接输出 Markdown，表格用 Markdown 表。

只问一个点（"这批卡能跑什么"）就只答那个点：结论 + 判据 + 一句「要完整方案说一声」，
不铺七章。**但并发口径声明和快照日期这两条，只要出现了并发或模型名就必须带上。**

载体只改**渲染密度**：短载体下每一项压到一两句，必填项仍然逐项都在。

## 只写确定能交付的能力

**私有化编队里不做自动分流**：编队里每个模型各自独立部署为一个 OpenAI 兼容端点，
**由应用侧按入口选固定端点**——这是应用配置，不是本方案在客户机器上交付的能力。客户要在
自己的卡上做平台级统一分流，写「需与供应商确认，本版不含」。

## Common Mistakes

| 错误 | 后果 |
|---|---|
| 把 roofline 数字当可承诺并发 | 高约一个数量级，签进 SLA 就是违约 |
