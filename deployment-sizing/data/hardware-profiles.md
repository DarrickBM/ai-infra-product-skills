# 硬件档案（公开版）

规格取自 NVIDIA 官方 datasheet 与公开资料。**这份档案没有工程实测数据**——它只支持
装载测算与 roofline 物理包络，不支持对外并发承诺。原因见每节末尾。

## H20-141GB（8 卡整机）

| 项 | 值 |
|---|---|
| GPU | HGX H20 × 8 @ 141 GB HBM3e = **1,128 GB** |
| 带宽 | **4.8 TB/s·卡**，整机 38.4 TB/s |
| FP8 / INT8 | 296 TFLOPS·卡，整机 2.37 PFLOPS |
| BF16 / FP16 | 148 TFLOPS·卡 |
| 互联 | NVLink + NVSwitch，卡间约 900 GB/s（TP4 / TP8 均可） |
| 精度 | FP8 / INT8 / BF16；INT4 weight-only 需按引擎实测；**不支持原生 FP4** |

**部署形态三原则**：

- 生产 SLA 优先 → **2×TP4 双实例**（有实例级冗余）
- 模型能力优先 → 1×TP8 单实例
- 高 QPS → 32B/70B 单卡或 TP2 多实例

**权重超 4 卡容量（141×4×0.92 ≈ 519 GB）的模型只能 TP8，无实例级冗余**——这条常常是
选型的隐藏判据。

## H20-96GB

同带宽同算力，只差容量：整机 768 GB（可用 706 GB）。差别不在「装不装得下」，在**装完
权重剩多少给 KV**。

## B300-288GB（HGX B300，8 卡整机）

| 项 | 值 |
|---|---|
| GPU | HGX B300（Blackwell Ultra）× 8 @ 288 GB HBM3e = **2,304 GB** |
| 带宽 | **8 TB/s·卡**，整机 64 TB/s |
| FP4（NVFP4） | 整机 108 PFLOPS 密集 / 144 PFLOPS 稀疏 → **13.5 PFLOPS·卡（密集）** |
| FP8 / FP6 | 整机 72 PFLOPS → **9 PFLOPS·卡** |
| BF16 / FP16 | 整机 36 PFLOPS → 4.5 PFLOPS·卡 |
| 互联 | 第五代 NVLink + NVSwitch，1.8 TB/s·卡（TP2/4/8 均可） |
| 精度 | **原生 NVFP4**、FP8 / FP6 / INT8 / BF16 |

**取值有两处坑，写方案前先确认客户那批卡到底是哪个 SKU：**

- **容量**：NVIDIA 文档写 288 GB/卡、整机 2.3 TB；部分整机厂商标 270 GB/卡、整机 2.1 TB
  （HBM 保留差异）。**按实测 `nvidia-smi` 的值取，拿不到就按 270 GB 保守算**，别直接抄 288。
- **算力**：公开表混用稀疏/密集口径（FP4 144 vs 108 PFLOPS）。**一律取密集值**；稀疏值
  不适用于推理装载测算。

**相对 H20 的三个结构性差别**：

1. **原生 NVFP4** → FP4 专家权重的模型按落盘体积直接跑。同一个 DeepSeek V4-Flash：
   H20 上要上转 FP8 约 294 GB，B300 上 167 GB。
2. **单卡 288 GB** → `weight_gb ≤ 288×0.92 ≈ 265 GB` 的模型 TP1 即可，8 副本；很多在
   H20 上被迫 TP8、无冗余的模型，到 B300 上能拿到实例级冗余。「权重超 4 卡容量只能
   TP8」那条 H20 判据在这里失效，**不要照搬**。
3. **带宽 8 TB/s（H20 的 1.67 倍）+ 显存 2 倍** → 显存基本不再是瓶颈。单机 B300 通常
   已经落进「权重占比 < 15%」那一档，**默认形态是每场景专用模型 + 多副本，不是
   「1 大 + N 小」**。

## GB300 NVL72（机架形态）

如果是 GB300 NVL72 而不是 HGX B300 整机：72 张 GPU 在**一个 NVLink 域**内，跨「节点」TP
不再需要 RDMA。此时「默认每台独立编队、不跨节点 TP」这条不成立，编队按整个 NVLink 域
规划。**先问清楚是 HGX 整机还是 NVL72 机架**——两者的编队结论完全不同。

## 多机与大规模

**默认每台独立编队、不跨节点 TP**——跨机 TP 要 RDMA（IB/RoCE），且只在单模型确实装不下
单机时才值得。先确认有没有 RDMA。

机器数变多时形态会翻转：单机紧约束下「1 大 + N 小」成立，是因为大模型吃掉大半显存；到
10 台 B300 这种规模，显存不再是瓶颈，问题变成「每类模型要几个副本、占几台机、留几台做
扩容与灰度」。这时按场景总并发反推副本数，而不是套单机的结构。

## 为什么这份档案不能用来做并发承诺

roofline 只建模显存带宽与算力的物理上限。它不建模预填充与解码互相挤占、请求排队、
P95 尾延迟——真实工程可承载的并发**比 roofline 低约一个数量级**。

所以本 skill 输出的所有并发数字都是**物理包络**，用来回答「上下文档位开不开得了、显存
够不够、结构合不合理」。**要能写进合同的并发与 SLA 数字，需要由供应商按实测工程数据
出具，或做 PoC 实测。** 这条必须写进每一份方案，不能省。

## 加新硬件

在 `scripts/fleet_sizing.py` 的 `HARDWARE` 里加一条，需要：单卡显存、单卡带宽、FP8 与
BF16 算力、卡数、`fp4_tflops`（无原生 FP4 填 0）、支持的精度。

档案里必须写清两件事，缺一条下一个人就会算错：**容量口径**（标称 vs 实测可用）、
**算力口径**（密集 vs 稀疏）。
